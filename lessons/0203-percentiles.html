Percentiles & Tail Latency

The p99 line on your dashboard and the "what's your latency target?" question in interviews ask the same thing. Today you learn to read response times as a distribution and see why the slowest 1% matters most.

2

Response time is a distribution

Send the same request a thousand times and you get a thousand different response times. Most are quick. A few are very slow, because of a garbage-collection pause, a lost packet, a cold cache, or a request stuck in a queue behind a slow one.[1] So "our latency" is not one number. It is a distribution.

The mean is the wrong summary for it, because it doesn't tell you how many users had that experience. Use percentiles instead. Sort every response time from fastest to slowest. The p50 (the median) is the value halfway down the list: half the requests were faster. The p99 is the value 99% of the way down: only 1 in 100 requests was slower. The slow end of the distribution is called the tail, so high percentiles like p99 and p999 are tail latencies.[1]

Normal requests take about 80 ms (median). Bars show how many requests landed at each response time. The x-axis is logarithmic.

Read the numbers

The simplest way to compute a percentile is the nearest-rank method. With n sorted values, pX is the value at position ⌈X/100 × n⌉, counting from 1. Tails get worse when you fan out

One user request often calls many backends in parallel and waits for all of them. Then the page is only as fast as its slowest call. Even if each backend is slow only rarely, the chance that at least one call is slow grows quickly with the number of calls. DDIA calls this tail latency amplification.[1]

If each call is slow with probability p, and the calls are independent, the page is slow with probability:

P(page slow) = 1 − (1 − p)n

Google's Jeff Dean and Luiz Barroso give an example. A server is slow on 1 request in 100. If a user request goes to just that server, 1% of users wait. If the request fans out to 100 such servers, 63% of user requests are slow.[2]

5

Measure honestly, then set a target

Measure from the client's side, with an open loop. A load-test client that waits for each response before it sends the next request slows down whenever the server slows down. Queues never build up, and the tail looks better than it really is. Real users don't wait for each other. Keep sending requests at a fixed rate, whatever the response time.[1] Gil Tene calls this measurement error coordinated omission.[3]

Never average percentiles. The mean of ten servers' p99s is not the fleet's p99. Averaging percentiles is mathematically meaningless. To combine data from several servers or time windows, add their histograms together, then read the percentile from the combined histogram.[1][5]

Then write the target down. Google's SRE book uses three terms.[4] A SLI (service level indicator) is a carefully defined measurement, such as p99 latency. A SLO (service level objective) is a target value for an SLI. A SLA (service level agreement) is a contract with users that says what happens if you miss the SLOs in it.

Say it in your own words

🎤 In the interview

When you state a latency requirement, give a percentile and a number: "Reads at p99 under 200 ms." When your design fans out (for example scatter-gather search, or a feed built from many services), say that it amplifies the tail. Then name a mitigation. One example is a hedged request: send a backup copy to another replica if the first is slow. In one Google benchmark, hedging after 10 ms cut p999 from 1,800 ms to 74 ms for only 2% more requests.[2]

Look at a latency dashboard you own. Does it show the mean, or percentiles? Do the percentiles come from merged histograms, or from averaging per-server values? The Ch 2 side quest walks you through it.
