Percentiles & Tail Latency

Response time is a distribution. Describe it with percentiles, watch the tail, and measure it honestly.

The vocabulary

TermMeansUse it for
MeanSum ÷ countThroughput and capacity maths. Not for describing user experience: outliers drag it.
p50 (median)Half of requests are fasterThe typical user's experience
p95 / p99 / p99995% / 99% / 99.9% are fasterThe tail: the users having a bad time
Tail latencyThe high percentilesSLOs, alerts, and interview requirements

Nearest rank: sort the n values. pX is the value at position ⌈X/100 × n⌉, counting from 1.

Tail latency amplification

One request fans out to n backends in parallel and waits for all of them. Each backend is slow with probability p:

P(slow) = 1 − (1 − p)ⁿ ≈ n·p (when n·p is small)

np = 1%p = 0.1%
11%0.1%
109.6%1.0%
6950%6.7%
10063%9.5%

With a large fan-out, each backend's p99 effectively becomes the page's median. Fixes include hedged requests: after a short delay, send a backup request to another replica.

Measure honestly

  • Measure on the client side. Response time = queueing + service time + network.
  • Run open-loop load tests. Send requests at a fixed rate, whatever the response time. A client that waits for each response hides queueing (coordinated omission).
  • Never average percentiles. Merge histograms across servers or time windows, then read the percentile.
  • Slow requests hold up others. A few slow requests can block everything queued behind them (head-of-line blocking).

SLI → SLO → SLA

  • SLI: a measurement. "p99 checkout latency per minute"
  • SLO: a target for the SLI. "< 400 ms in 99.9% of minutes"
  • SLA: a contract, with consequences for missing it. "credit if missed"

Say it in an interview

"The read path target is p99 under 200 ms. This page fans out to about 20 services, so even at 1% slow per call, about 18% of page loads would hit a slow call. I'd give each dependency a tighter p99 budget, and hedge the reads that matter most."
